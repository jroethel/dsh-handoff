Ultimate Fleet Guide

The single page to come back to: what every file in the kit is, the order to do them in, and where the plain Markdown holds the canonical detail.

How to use this page. It is the map, not the contract. The INSTALL.md checkpoints and the DEPLOY.md runbook are the sources of record for commands and wording; edit prose there, not here. Work the checkpoints one at a time and return to the chat with next when a check passes.

1The system, and why it is shaped this way

Every project is its own Ultimate process on its own pinned port. A hub is an ordinary project whose AGENTS.md charter turns its @ultimate into the coordinator; spokes need nothing installed. Decisions this kit bakes in:

  • Hub on the VPS. The hub's value is uptime: sweeps fire, its cache stays warm, watchdog retries land.
  • Spokes are headless. --no-open everywhere; the hub's UI is the one browser tab.
  • Laptop spokes sleep when the lid shuts. Asleep is a normal state, not an incident; the charter says so.
  • Tailscale only. The hub is tailnet-only; that is the security model. SSH tunnels are fine for your own eyeballs, never for hub-to-spoke.

How the hub finds a spoke, in order (this is why spokes can be local and remote):

  1. Its own storage, when the project runs on the hub's machine.
  2. Loopback: any running instance on the same machine.
  3. The remotes user setting (machine → project → Tailscale URL), which this kit fills.
  4. The cloud register, when cloud backups are on.

3The order to do them in

Do checkpoints in order; each names its machine and ends with a check. Full wording: INSTALL.md; terse commands: DEPLOY.md.

laptop 0 · Fill the roster. Edit wiring/fleet.json: paths, user names, ports, DNS names (DNS can wait). Check: no REPLACE-me left except unknown DNS.
INSTALL.md checkpoint 0 · DEPLOY.md Stage 0
vps 1 · Provision the VPS. scp -r the kit up, run linux/provision-vps.sh, then by hand: sudo tailscale up, operator, HTTPS certificates in the admin console, linger. Check: tailscale status works, ultimate --help works.
INSTALL.md checkpoint 1 · DEPLOY.md Stage 1
vps 2 · Deploy the hub repo. git init ~/fleet-work/hub, copy hub/ plus the roster, enroll.sh fleet, open https://<vps>:4747, provider login, approve the project trust card. Check: hub answers; tailnet chip green; Extensions tab lists fleet.
INSTALL.md checkpoint 2 · DEPLOY.md Stage 2
browser 3 · Smoke-test hub to spoke. FIRST-PROMPT 1 then 2: orient, then one sweep. Laptop spokes read asleep with the lid shut; a 403 is allowlist wiring. Check: the sweep ends with a counts line and names loopback vs tailnet per spoke.
INSTALL.md checkpoint 3 · DEPLOY.md Stage 6
vps 4 · Enroll VPS spokes. Clone each real project to ~/fleet-work/<name>, then enroll.sh <name>. Check: each ends healthy; the Fleet panel shows green.
INSTALL.md checkpoint 4 · DEPLOY.md Stage 3
laptop 5 · Laptop spokes. pnpm add -g the clone (once), merge the tailscale user-settings shape, ./darwin/fleet install && ./darwin/fleet status. Check: running · api ok per spoke; fleet remotes prints the next step's JSON.
INSTALL.md checkpoint 5 · DEPLOY.md Stage 4
vps 6 · Wire laptop spokes into the hub. Merge fleet remotes output into the VPS ~/.ultimate/settings.json; it reloads live. Check: sweep shows laptop spokes asleep or healthy, no 403s.
INSTALL.md checkpoint 6 · DEPLOY.md Stage 5
browser 7 · Make it standing. FIRST-PROMPT 3: the 9am weekday sweep automation. Optionally ask @ultimate to review the charter and harden the panel. Check: the automation confirms its next fire time.
INSTALL.md checkpoint 7 · DEPLOY.md Stage 6

4Day one, in the hub's own words

  • Orient: read charter and roster, answer in five lines, start nothing.
  • First sweep: follow fleet-sweep exactly; report which calls were loopback vs tailnet.
  • Standing: create the Morning sweep automation, subscribe @ultimate.

Verbatim prompts: hub/FIRST-PROMPT.md

5Mobile: Tailscale on your phone

Built in, verified path; prereqs are the tailnet app on the phone and HTTPS certificates enabled upstream.

  • The whole UI as an app: the hub's tailnet chip shows the URL as a QR code. iPhone: Safari, Add to Home Screen, Open as Web App. Android: Chrome menu, Install app.
  • Web Push: enable the push extension, then the notify bell per device. Questions arrive answerable from the notification (Reply, and Approve when answers are recommended), plus landings and failed runs.
  • Share sheet: with the Android app installed, share links and text from any app into the hub's composer.

Full setup: DEPLOY.md, Mobile access section

7Later, on purpose

  • Social apps (Slack, Discord, Telegram): nothing ships upstream and the hub has no public endpoint by design. The working shape, deferred: a bridge bot on the VPS using each platform's outbound-only transport, allowlisting your user IDs, talking to the hub over loopback actions; short replies to the thread, long jobs fire-and-forget with Web Push for outcomes. One small Node service and one more systemd unit when wanted.
  • Push rules in the fleet extension: a VPS spoke going down or a sweep finding failures could call PushApi.notify, so the phone learns before the morning sweep.
  • Cloud backups (off by default): per-chapter backups, and their register is the fourth lookup in the resolution chain.

8Addendum: the trusted-identity design, on Ultimate

The trusted-identity brainstorm (2026-11-14, one directory up from this kit) designs a durable, trusted agent for DSH: durable hands, a Lume-style identity with soul and journals, factory templates the agent builds itself, executed verification, time-typed records, and a governance layer. Mapped onto Ultimate, several of its build items already exist: the "port" it planned is unnecessary, because Ultimate runs on and patches pi-durable directly. Verdicts below: native (shipped), partial (needs a small extension or a knob), build (new code).

What to build (three small extensions, everything else is prose):
  • identity/constitution: soul and narrative as durable documents, injected as a stable prompt section; hash pins over soul, charter and settings, verified at open.
  • ledger: verdict rows (model, task type, first-try vs rescued) with valid windows and baselines, over the trace and event streams the harness already keeps.
  • triggers: authenticated inbound webhooks over an extension action admitted by Tailscale identity, dispatching like an automation fire.

The one-afternoon MVP, translated. It gets smaller here: create the project, onboard (writes the first memories), write the charter, add the soul section, one automation waking @ultimate with the choose-again prompt, lander.checks left empty at first so everything is reported (staged autonomy). Chapters and dream give consolidation and compounding for free. Two weeks of real work answers the brainstorm's testable question, optionally with the DSH resident as the control.
